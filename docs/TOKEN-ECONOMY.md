# Token 账：怎么量、量到多少

这份文档只讲一件事：**上下文里「留在那儿」的东西，比「拿进来一次」的东西贵得多。**

---

## 一、成本模型

一次 LLM 请求的输入 = 系统提示 + 全部历史 + 本轮新内容。也就是说：

> **任何进入上下文的东西，都不会只付费一次。它会在之后每一轮里被重发、被重新计费，直到会话结束或被压缩。**

由此得到两个可测量的量：

| 指标 | 定义 | 优化方向 |
|---|---|---|
| **常驻成本** | 每轮都要重发的东西（系统提示、注入的记忆、加载过的技能全文） | 尽量小，只放跨场景通用的 |
| **检索成本** | 为了找到一条信息而读进来的中间量（索引、总览、整份文档） | 只取命中片段 |

绝大多数「记忆方案很贵」的问题，出在**把检索成本固化成了常驻成本**：为了查一次而读进来的索引，会一直躺在上下文里陪跑到会话结束。

---

## 二、先解决度量口径（踩过的坑）

**字符数 ≠ 字节数。** 中文 UTF-8 一个字占 3 字节，把字节数当字符数报，账会虚高到 3 倍。

真实事故：一份索引文件 `4,658 字节`被当成「4,658 字符」，据此算出的百分比全错，结论要重算。

正确的量法：

```powershell
# 字符数（用于 token 估算）
(Get-Content file.md -Raw).Length
# 字节数（用于磁盘占用）
(Get-Item file.md).Length
```

```bash
# Node 里
readFileSync(f, 'utf8').length                      // 字符
Buffer.byteLength(readFileSync(f, 'utf8'), 'utf8')  // 字节
```

估算 token：中文为主的内容按 **1 字符 ≈ 0.6–0.7 token** 估；英文按 4 字符 ≈ 1 token。要精确就用对应模型的 tokenizer 实测——但**别用估值当结论**，先量字符。

## 三、实测：摘要 vs 全文

一次真实样本（某 agent 的技能目录）：

| 量 | 数值 |
|---|---|
| 全部技能正文合计 | 271,295 字符 |
| 常驻的技能摘要（每条一句话） | 2,461 字符 |
| 摘要占比 | **0.91%** |

结论：**「挂 N 个技能/记忆会不会爆上下文」的答案是「不会爆，但要付摘要税」**。

- 每个摘要平均 107 字符 → 挂 100 个 ≈ 10,700 字符/轮常驻（约 7k token）
- 但一旦调用，正文全文会进来**并且留驻**——调用 100 个 = 27 万字符，那才是真的爆

所以「挂载」和「调用」是两个量级的事，别混为一谈。

## 四、实测：读索引 vs query

同一个记忆库（146 条明细 / 12 个主题 / 顶层 26 条一句话）：

| 查法 | 读进来的量 |
|---|---|
| 旧：SUMMARY.md + INDEX.md + 命中的主题正文 | 11,040 – 12,841 字符 |
| 新：`query "关键词"` 只回前 5 条 | 737 – 1,100 字符 |
| **省** | **91 – 94%** |

12 组关键词实测平均输出 **624 字符/次**（命中的 9 组平均 738；未命中的 3 组只输出 54 字符的提示）。

## 五、复利：把「省一次」换算成「省一场会话」

假设会话还剩 R 轮，那么**省下的量 × R** 才是真正的账：

| 场景 | 旧做法 | 本方案 |
|---|---|---|
| R = 26 轮（30 轮会话，第 5 轮查 1 次） | 26 × 11,819 ≈ **307,294 字符** | 26 × 738 + 注入增量 ≈ **21,798 字符** |

省下约 285,500 字符 ≈ 20 万 token 的累计输入。

### 回本点

本方案为了让 agent 知道「先跑 query」，在全局指令里多写了一句说明，成本是 **+87 字符/轮**：

```
一次查询省 11,081 字符 ÷ 87 字符/轮 ≈ 127 轮
```

也就是说：**一次查询就能回本 127 轮的注入增量**。唯一的亏法是「一整个会话都不查记忆」——30 轮白付 2,610 字符（约 1.8k token）。

这个取舍值得：记忆查询的收益是长尾的，而成本是恒定的。

### 插件形态的边际成本

把同一套检索包成模型可调用的工具（本项目的「方式 A」）时，唯一的常驻新增是**工具 schema**：
名称 + 描述 + 参数说明，约 **50–100 token/轮**。换来的是 agent 不必再敲 shell、
也不必把命令输出转述一遍（那一次往返本身就是几千字符的上下文）。

对比一下量级：每轮自动注入式记忆约 2.7 KB（≈1.9k token）／轮，而本项目是 0 ＋ 一个工具 schema。
**两者差两个数量级**——这也解释了为什么「工具型插件」比「注入型插件」省得多。

## 六、三条通用纪律

1. **注入即负债**：每轮注入的东西要按「× 剩余轮数」来估价，而不是按「一次多少钱」。
2. **先量再算**：说「这个方案省 90%」之前，必须给出「读了多少、写了多少、增量百分比」——结构性数据，不是感觉。
3. **长会话主动收拾**：上下文膨胀到影响效果时，先落盘（把结论写进记忆库），再压缩。**落盘之后压缩是安全的，没落盘就压缩是丢记忆。**

## 七、自测清单

拿你自己的配置量一遍，五个数：

- [ ] 常驻提示（系统提示 + 注入记忆 + 技能摘要）有多少字符？
- [ ] 其中有多少是「每轮都在、但多数轮次用不上」的？
- [ ] 查一次记忆要读进来多少字符？能不能只取命中片段？
- [ ] 你这个会话已经进行了多少轮？（把上面的数 × 轮数）
- [ ] 有没有「同一份内容被抓了两次」的地方？（重复读取是纯粹的白烧）

第一项 × 会话轮数，通常就能解释「为什么这个会话这么贵」。
